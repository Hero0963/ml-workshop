0. 結論先講

整條「拿官方模型 → 本機 GPU 推論 → 解析成 Puzzle → 餵 CP-SAT」的路是通的。 四種模型／量化組合全部 100% 載入 GPU、無 CPU offload，16GB 顯卡對 4B 級 Q8 綽綽有餘。

但未微調的端到端正確率極低：六張圖只有 1 張完全正確（qwen3.5:4b-q8_0 對 puzzle_03）， gemma4:e4b 是 0/6。P2–P4 的合成資料與微調有明確必要性。

唯一的共同瓶頸是「牆」，不是「認字」。 最佳設定（qwen3.5:4b-q8_0 ＋ 關閉思考，見 §3.3）在六張圖上 JSON 6/6、格盤尺寸 6/6 全對、逐格 0.924、號碼 0.910——格盤與數字幾乎讀滿分， 牆 F1 卻只有 0.410（puzzle_01 10 道中 2 道、puzzle_04 14 道中 1 道）。 計畫書把「牆召回率低」列為風險第 2 名，實測直接坐實，而且它幾乎是唯一擋住端到端的東西。

兩個零訓練成本的介入就把成績推上去了——關閉思考（§3.3）與加入格盤尺寸指示＋7×7 範例（§3.4）。 qwen3.5:4b-q8_0 的 JSON 解析率 3/6 → 6/6、逐格 → 0.961、 端到端相符 → 2/6、延遲 44.5s → 5.4s。

但同樣這兩個介入都讓 gemma4:e4b 變差。 在投入任何訓練成本前，這類設定必須逐模型實測，不可跨模型沿用； 而「對介入的穩定度」本身就是選型訊號（見 §9.2）。

目前最佳未微調設定 ＝ qwen3.5:4b-q8_0 ＋ 關閉思考 ＋ --prompt sized。 這就是微調必須超越的門檻。

四層指標

  1. JSON 可解析率——能否抽出並通過 SimplePuzzleOutput 驗證
  2. 結構準確度——逐格準確率、號碼格召回率（單獨列，因為號碼是少數，全空盤也能拿高逐格分）、牆 precision／recall／F1
  3. 端到端——預測結果餵 CP-SAT，記錄「解得出來」與「路徑與 ground truth 逐格相符」兩個不同的欄位
  4. 成本——牆鐘延遲、Ollama 自報的 load／eval 拆分、token 數、GPU 峰值

評分邏輯自檢過才用：把六題的 ground truth 當成「完美預測」餵回評分函式，確認逐格 1.000／牆 F1 1.000／端到端路徑逐格相符； 另加形狀不符、全漏牆、無牆題、部分命中、儲存格拼寫變體（"1"／" 7 "／"XX"）、不可解預測、超大盤拒絕共 8 組邊界案例，全數通過。 沒有這一步，下面的表格都不可信。

2.1 Q4 vs Q8：差異是災難級的，而且兩個家族方向相反

qwen3.5:4b 的 Q4 完全不可用。它思考了 16,505 字元、燒掉 6,215 個 output token 直到預算用盡， 從頭到尾沒有吐出任何 JSON，冷暖兩次皆然。換成 Q8 之後只用 530 token、6.2 秒，版面逐格全對、8 個號碼全對。 同一個模型、同一張圖、只差量化，結果是「完全失敗」與「版面滿分」。

gemma4:e4b 反而是 Q8 更差。Q4 讀對了 6×6，Q8 讀成 7×6（多一列），冷暖兩次一致，不是抖動。

實務結論：不能假設「量化越高越好」，也不能跨家族沿用同一個量化選擇。這個對照本身就值回 P0 的成本。

2.2 已排除的風險

  • 16GB 顯卡跑 4B 級 Q8 不是瓶頸：最吃的 gemma4:e4b-it-q8_0 峰值 9582 MiB，四組全部 100% GPU，無 CPU offload。
  • 容器內 Ollama 版本：0.16.1 確實跑不動 2026 年的模型，docker compose pull ollama 後為 0.32.13， 15GB 舊模型（openbmb/minicpm-o2.6 等）因 volume 已 pin 而完整存活。
  • ollama ps 與 nvidia-smi 對不上：gemma4:e4b 磁碟 9.6GB、ps 報 3.4GB、實際增量 4707 MiB。 這與 Gemma 4 E4B 的 nested／effective-params 設計方向一致，但機制未經一手來源確認，僅列為觀察值。容量規劃請用 nvidia-smi 增量，不要用 ps 的 SIZE。

兩個具體且可修的失敗模式：

  • 格盤尺寸偏誤：puzzle_04 與 puzzle_06 實際是 7×7，模型硬讀成 6×6。不是讀錯個別格子，是整個尺寸判斷失準—— 而 few-shot prompt 裡三個範例全部是 6×6，模型很可能是被範例帶偏的。這正是 P2 增強（5×5–8×8）要打的東西。
  • 牆的偽陽性和偽陰性一樣致命：puzzle_03 版面滿分、4 道真牆全中，卻仍解不出來——因為它多幻覺了 2 道不存在的牆（precision 0.667）。 評估牆時不能只看 recall。

它的失敗不是「看不懂」，是「話太多講不完」。三次失敗的 thinking 都在 20,000–26,000 字元、output token 撞到 6,200–6,600 的天花板， 根本沒輪到吐 JSON。而成功的三次思考只有 886–9,409 字元。

更值得注意：失敗的 puzzle_04／puzzle_06 正是兩張 7×7 大盤，puzzle_02 則是 12 個號碼的密集盤——盤面越複雜、思考越長、越容易撞頂。 這是推論設定問題，不是模型能力問題，理論上不必微調就能修（見 §4）。

§3.2 顯示 qwen 的失敗是思考撞頂，於是把兩個模型都用 --no-think 重跑六張圖。這是零訓練成本的推論設定改動。

關閉思考讓 qwen3.5:4b-q8_0 全面翻盤：JSON 解析率 3/6 → 6/6、 格盤尺寸 6/6 全對（含兩張先前完全答不出來的 7×7）、延遲快 5.8 倍、 output token 由約 6,000 降到 236–562。先前讀不出 7×7 不是看不懂，是思考爆掉沒機會作答。

而 gemma4:e4b 方向相反——關掉思考全面變差（尺寸 4/6 → 3/6、逐格 0.444 → 0.389、牆 F1 0.268 → 0.127）。 思考對 gemma4 是有用的，對 qwen 是有害的；這個開關必須逐模型實測，不能沿用。

但端到端仍卡在 1/6。最佳設定（qwen3.5:4b-q8_0 ＋ 關閉思考）的版面已接近可用 （逐格 0.924、號碼 0.910、尺寸全對），牆 F1 卻只有 0.410—— puzzle_01 10 道中 2 道、puzzle_04 14 道中 1 道。 這把本報告的主結論收得更緊：剩下的問題幾乎純粹是牆。

3.4 消融：加入格盤尺寸指示與 7×7 範例（--prompt sized）

§3.1 顯示兩個模型都把 7×7 讀成 6×6，而 baseline prompt 的三個範例全部是 6×6。 於是做第二個零訓練成本的介入：加一句「先數列數與行數，格盤常見 5×5／7×7／8×8」，並補一個 7×7 範例。 該範例是合成的（出題器 seed=20260815，CP-SAT 驗過可解）， 刻意不用 puzzle_04／puzzle_06——它們是評估集，放進 prompt 就是洩題。

但要看是哪一題變對的。puzzle_01–03 的答案本來就寫在 few-shot prompt 裡（洩題）。 原本唯一答對的 puzzle_03 屬於洩題；新增答對的是 puzzle_05，它不在 prompt 裡。 所以真正具泛化意義的答對數是 0 → 1，這比表面的 1 → 2 更值得記。

4. 兩個指標設計的坑（我自己踩到的）

4.1 無牆題會把牆 F1 灌水

puzzle_02 與 puzzle_06 本來就沒有牆，模型預測 0 道就自動拿到 F1 = 1.0。 這讓 gemma4:e4b 的牆 F1 平均從真實的 0.268 被抬到 0.512，幾乎翻倍。 已在工具中加入 mean_wall_f1_walled_only 與 walled_puzzles 欄位。之後比較微調成效請看有牆子集，不要看總平均。

4.2 seed ＋ temperature=0 不保證決定性

我一度根據兩次相同結果就宣稱設定是決定性的，跑滿八次後不成立： gemma4:e4b Q4 冷、暖兩次給出不同答案（逐格 0.639 vs 0.667、牆 12 道 vs 9 道）； qwen3.5:4b-q8_0 與 gemma4 Q8 則完全穩定。 決定性是模型相依的，不是設定保證的——後續所有對照都要多次重複取平均，不能用單次結果下結論。

7. 建議的下一步

  1. 已完成：關閉思考的消融（§3.3）。qwen3.5:4b-q8_0 JSON 3/6 → 6/6、尺寸 6/6、延遲快 5.8 倍； gemma4:e4b 反而變差。此開關要逐模型設定，不可共用。
  2. P2 的重心要從「全面模仿」收斂到「把牆畫對」。這是本報告最重要的方向修正： 版面與數字辨識在未微調狀態下已接近可用（逐格 0.924、號碼 0.910）， 合成資料與微調的投資報酬幾乎全部集中在牆——牆的粗細、位置（壓在格線上）、與格線的對比、 以及 0–16 的數量分布，都要比其他增強優先。
  3. 評估牆要同時盯 precision 與 recall。gemma4 在 puzzle_03 真牆 4/4 全中卻仍解不出來， 就是多幻覺了 2 道。只看 recall 會誤判成「快好了」。
  4. 已完成：加入格盤尺寸指示與 7×7 範例（§3.4）。 qwen3.5:4b-q8_0 逐格 0.924 → 0.961、牆 F1 0.410 → 0.438、端到端相符 1/6 → 2/6、延遲 7.7s → 5.4s； gemma4:e4b 再次變差（過度矯正，把 6×6 讀成 7×7）。 目前最佳未微調設定 ＝ qwen3.5:4b-q8_0 ＋ 關閉思考 ＋ sized prompt，這就是微調要超越的門檻。
  5. 微調首選仍是 Gemma 4 E4B（免費 T4 唯一走得通的 QLoRA 路徑，官方 Gemma4_(E4B)-Vision.ipynb）， 但請把未微調的「qwen3.5:4b-q8_0 ＋ 關閉思考」留在評估表當門檻： 微調後若贏不過它，代表該換家族，而不是加訓練量。 注意這個門檻比原本想的高得多——它已經拿下尺寸 6/6、逐格 0.924。

8. 未驗證與限制

  • 每個設定只跑 1–2 次。已知 gemma4:e4b 不決定性，因此其單題數字有抖動，不應被當成精確值。
  • P1 的 GPU 峰值不可用：P1 連續跑兩個模型時前一個仍常駐，峰值被污染（13,483 MiB）。VRAM 請只採用 §2 的 P0 數字。
  • 只有 6 張真實截圖，且它們同時是 few-shot 範例的來源（puzzle_01–03 的答案就寫在 prompt 裡）。 puzzle_01 與 puzzle_03 的成績有洩題成分，不能當泛化證據。這使 P3 的真實驗證集更重要。
  • ollama ps 的 SIZE 與實際 VRAM 增量不符的機制未經一手來源確認。
  • llama.cpp 對 DiffusionGemma 的支援狀態僅有二手來源，未驗。

核心結論：世代選擇是被「尺寸」決定的，不是被「效能」決定的。

推薦：先訓 Qwen3.5-4B（若成本不是硬限制）。 兩者的 notebook 條件相同，差別全在起點——Qwen 只需要學會讀牆，Gemma 得同時學會格盤尺寸、數字與牆。 單一目標的訓練，收斂與除錯都遠比三個目標一起打好處理，而合成資料 pipeline 正好最擅長教牆。

第三個理由（§3.3 ＋ §3.4 的共同觀察）：gemma4:e4b 對介入不穩定。 兩次零成本介入——關閉思考、加入格盤尺寸指示——都是幫 qwen、害 gemma； 後者甚至被「格盤常常不是 6×6」帶到把真正的 6×6 過度矯正成 7×7。 一個連 prompt 指令都吸收不穩的模型，微調的除錯成本會高得多。

唯一的翻轉條件：若「只用免費 Colab 層」是硬限制，改選 Gemma 4 E4B—— 它的 QLoRA 10GB 是免費 T4 上唯一走得通的路徑。

與 Unsloth 官方建議相反的一項操作提醒： 官方建議先設 finetune_vision_layers = False（省記憶體）。 但本報告顯示本任務的失敗模式是純視覺的——數字與版面模型早已讀對，錯的是壓在格線上的細黑牆棒。 凍住視覺層很可能什麼都學不到，因此這個消融要優先做，而不是當作有空再補。

另一個實用細節：Unsloth 文件註明 Gemma 4 E2B／E4B 這類多模態模型訓練時 loss 落在 13–15 是正常的（純文字版才 1–3）。不知道會誤判成訓練發散。

出處（一手，查證日 2026-08-15）： Unsloth · Qwen3.5 Fine-tuning （原文：“It is not recommended to do QLoRA (4-bit) training on the Qwen3.5 models, no matter MoE or dense, due to higher than normal quantization differences.”；bf16 LoRA 0.8B 3GB／2B 5GB／4B 10GB／9B 22GB／27B 56GB）、 Unsloth · Gemma 4 Fine-tuning （E2B LoRA 8–10GB／QLoRA 8GB；E4B LoRA 17GB／QLoRA 10GB）、 Unsloth notebook 索引。

9.3 DiffusionGemma 為什麼不採用（曾被特別問到）

它是離散擴散語言模型：不是逐 token 生成，而是從噪聲畫布平行去噪 256-token 區塊， Google 宣稱單張 H100 超過 1000 tokens/s、RTX 5090 超過 700 tokens/s。對「一次吐一大包 JSON」這種任務， 理論上很有吸引力。但三個硬限制同時成立：

  1. 放不進 16GB——Google 官方 blog 自己寫「量化後 fits comfortably within 18GB VRAM」，Unsloth 文件列 Q4_K_M 需 18GB。 對比我們實測 gemma4:e4b Q4 的 GPU 增量只有 4.7GB。
  2. 不在 Ollama library（registry 探測 404）——本專案的部署鏈是 Docker ＋ Ollama，整條要換掉。llama.cpp 支援據二手來源仍在未合併 PR。未驗
  3. 微調要 A100——與「免費 Colab T4」的前提直接衝突。

另外影像能力的來源互相矛盾，需注意：官方模型卡寫 「Processes interleaved text, image (with variable aspect ratio and resolution support), and video inputs」， 但官方 blog 通篇只談文字生成、未提影像輸入。兩者都是一手來源卻不一致——真要用必須先自己實測，不能照抄任一邊。

唯一值得持續追蹤之處在姊妹 RL track：Unsloth 的 notebook 索引裡 DiffusionGemma 只有一本， 就是 26B-A4B Sudoku GRPO，而 Sudoku 與 Zip 同屬「網格＋硬約束＋可程式驗證」。同樣卡 A100。

9.4 怎麼重驗這一節（給未來的接手者）

不要只讀排行榜或列表型文章——它們可以告訴你「有哪些家族」，不能決定「該家族最新第幾版」。照以下順序做：

  1. 反向探測有沒有更新世代（最便宜、最有效）： 
    for m in qwen3.9 qwen4 gemma5; do curl -s -o /dev/null -w "$m %{http_code}\n" \
  "https://registry.ollama.ai/v2/library/$m/manifests/latest"; done
    200 代表存在、404 代表沒有。這是本節每一列「有／沒有」欄位的產生方式。
  2. 用工具鏈索引決定「現在真的能跑什麼」：ollama.com/library/<name>/tags 給尺寸與量化， Unsloth notebook 索引給「能不能訓」。二手名單與工具鏈打架時以工具鏈為準。
  3. 發布日回一手：Gemma 用 官方 releases 時間軸（有精確到日）； Qwen 官方沒有等價頁面，只能用 HF org 依建立時間排序 ——注意那顯示的是「最後更新」不是「發布日」，只能當下界，要標未驗。
  4. 驗證要對稱：不可以 A 家族查一手、B 家族抄部落格。本節六個世代都跑了同一套流程。
