| 問題 | 答案 |
|---|---|
| 兩個 goal 達標了嗎 | **都達標**（best-of-32）：4×4 **0.9917**、6×6 **0.8535**。⚠ 6×6 只比門檻高 0.0035，評估雜訊就有 ±0.01 |

## 1. goal 判定

判定基準依 2026-09-11 定案為 **best-of-32**（本人：這是練習用專案，不在 N=32 vs 64 上著墨）。

| goal | deterministic | best-of-32 | 門檻 | 狀態 |
|---|---|---|---|---|
| `goal1_4x4` | **0.9404**（`bc_multi_456`）| **0.9917**（1.55 次／題）| 0.90 | ✅ |
| `goal2_6x6` | **0.5205**（`bc_multi_456`）| **0.8535**（7.76 次／題）| 0.85 | ✅ |

舊的單尺寸模型（給歷史對照）：4×4 det 0.8947；6×6 det 0.4620、best-of-32 **0.8500**（8.05 次／題）。
**現在服務的是多尺寸模型**，6×6 的 best-of-32 從 0.8500 變成 **0.8535**——仍然貼著門檻。

⚠ **0.8500 剛好等於門檻（1,700／2,000），而 best-of-N 的評估雜訊約 ±0.01。**
同一個模型、同一份測試集，只因為抽樣 rng 串流不同（上一輪跑到 N=16 就停、這一輪跑到 64），
N=16 的分數就從 0.8000 變成 0.8105。**所以「達標」要連著這句話一起講，best-of-64 = 0.8835 才是有餘裕的那個。**

## 2. ★ 多尺寸模型 vs 單尺寸專用模型

**問題**：4×4／5×5／6×6 要三個模型，還是一個？

**做法**：新生一份 4／5／6 的資料集（`seed20300000_n20000_456`，60,000 題，11m16s），
在**同一份資料、同一組測試集**上訓練四個模型——一個混合尺寸的，三個單尺寸的——行為克隆、10 epochs、其餘設定相同。

### deterministic solve rate（held-out test）

| 盤面 | 多尺寸 `bc_multi_456` | 單尺寸對照 | 差 |
|---|---|---|---|
| 4×4（1,931 題）| **0.9404** | 0.9042（`bc_ctrl_4x4`）| **+0.0362** |
| 5×5（2,001 題）| **0.7496** | 0.7131（`bc_ctrl_5x5`）| **+0.0365** |
| 6×6（2,000 題）| **0.5205** | 0.4890（`bc_ctrl_6x6`）| **+0.0315** |

### best-of-32（同一份測試集，`--max-attempts 32`）

| 盤面 | 多尺寸 | 單尺寸對照 | 差 | 多尺寸的嘗試次數 | 對照的嘗試次數 |
|---|---|---|---|---|---|
| 4×4 | 0.9917 | **0.9938** | **−0.0021** | **1.55** | 1.61 |
| 5×5 | **0.9495** | 0.9330 | **+0.0165** | **3.59** | 4.33 |
| 6×6 | **0.8535** | 0.8520 | **+0.0015** | **7.76** | 8.02 |

### 判讀（★ best-of-32 改變了結論的形狀，不要只看 deterministic）

- **deterministic：三個盤面全部是多尺寸領先**，差距 +0.032 ~ +0.037，
  三個互相獨立的盤面同方向、同量級。單看任一個都落在 ±0.02–0.04 雜訊地板內，
  **站得住的是方向一致性，不是任一個數字**。
- **加上推論預算後兩邊打平**：4×4 **−0.0021**、6×6 **+0.0015**，都遠小於評估雜訊（±0.01）；
  只有 5×5 還留 **+0.0165**。機制很直接：best-of-32 讓兩邊都往同一個上限逼近。
  ⚠ **這不是「多尺寸沒用」**——這一欄要回答的問題是「多尺寸**比較好**嗎」，
  而這個專案要的是「**一個模型能不能取代三個**」，那是另一個問題，答案是**能**。
- **打平的同時它更便宜**：同一個 N 下三個盤面都用更少的嘗試次數
  （1.55／3.59／7.76 vs 1.61／4.33／8.02），5×5 省 **17%**。
- ⇒ **目標達成**：一個模型取代三個，**deterministic 更好、best-of-32 打平、推論更便宜、
  訓練成本略低**，而且 **5×5 從沒有模型變成 0.7496／best-of-32 0.9495**。
  要三個尺寸都好，現在只要維護一個 checkpoint。
- ⚠ **6×6 的 seed 雜訊仍然沒量過**（用 BC 量只要約 16 分鐘）。
- **這推翻了我自己在計畫書 §2 寫下的風險**：「混合尺寸很可能改善 4×4／5×5，
  但**沒有機制理由**能改善 6×6」。6×6 的 deterministic 從舊模型的 0.4620 變成 **0.5205**。
  合理的事後解釋是**小盤面提供了密度更高的長程規劃訊號**（4×4 每局只要連對 15 步就有回饋，
  6×6 要 35 步），也就是一種**免費的 curriculum**——但這是事後解釋，**沒有實驗支持**，
  要驗證得另外設計（例如只用 4×4+6×6、不含 5×5 的臂）。

### 附帶結論

- **5×5 從「沒有模型」變成「有模型」**：現行資料集原本只有尺寸 4 和 6（名稱裡的 `4-6` 是範圍標籤不是清單），
  所以 5×5 從來沒被訓練過。
- 訓練成本：多尺寸 **465.3 秒** vs 三個單尺寸合計 **478.1 秒**（100.1 ＋ 149.7 ＋ 228.3）⇒ **一個模型比三個略便宜，而且三個盤面都比較好**。

## 3. ⓪ value-coef 對照（擋在 PPO 微調前面的那個問題）

2026-09-05 給 BC 加了 value head，讓 PPO 微調有 critic 可用，但**當時沒量它會不會傷到策略**——
小規模煙霧測試看起來偏低，而且 policy 與 value 共用同一個卷積骨幹，擔憂是合理的。

**同一個 goal、同一個 seed、同一份資料，只差 `--value-coef`：**

| 臂 | val_choice_accuracy | deterministic solve |
|---|---|---|
| `bc_ctrl_4x4`（`--value-coef 0.5`）| 0.8770 | 0.9042 |
| `bc_ctrl_4x4_valuefree`（`--value-coef 0`）| 0.8777 | **0.9125** |
| 差 | −0.0007 | **−0.0083** |

⇒ **差距在 ±0.02–0.04 的雜訊地板內，沒有證據支持 value 回歸會傷到策略。**
煙霧測試看到的下降沒有在完整訓練裡重現。

⚠ 誠實邊界：這是**同 seed 的配對比較**，只能說「在這個 seed 上沒有受傷的證據」，
不能說「證明無害」。但它足以**解除 BC → PPO 微調的前置封鎖**。

## 4. 跨尺寸泛化（2026-09-11 量的，解釋了為什麼多尺寸值得試）

拿現成模型丟到它沒訓練過的盤面上（deterministic）：

| 模型 ＼ 盤面 | 4×4 | 5×5 | 6×6 |
|---|---|---|---|
| `bc_4x4` | **0.8947** | 0.0706 | 0.0105 |
| `bc_6x6` | 0.5456 | **0.2941** | **0.4620** |
| greedy 對照 | 0.1170 | 0.0176 | 0.0041 |

**泛化是單向的**：大盤面模型往下相容（6×6 模型沒看過 4×4 就有 0.5456，是 greedy 的 4.7 倍），
**小盤面模型往上完全不行**（4×4 模型在 6×6 只有 0.0105，約等於 greedy）。

**為什麼不用改任何程式就能量**：觀測一律 padding 到 8×8（`rl_env_v2.py:122`），
純量帶 `height/8`、`width/8`（`:350`），而 `_load_sample()` 每一局重讀高寬（`:133`）
⇒ 任何 checkpoint 都吃得下任何 ≤8×8 的盤面，一個 env 也能混著吃不同尺寸。
`Goal` 從 `size: int` 改成 `sizes: tuple[int, ...]` 是這次唯一需要的改動（三個呼叫點）。

## 5. A5：RL solver 掛進 API

新增 `src/core/rl/solver_service.py`，是 `src/core/rl/` 裡**唯一**被實驗腳本以外的東西使用的檔案。

- **重用評估用的同一條路徑**（同一個 env、同一套動作遮罩、同一個 rollout 迴圈）
  ⇒ 報告裡的數字就是這個端點交付的數字。
- **推論不需要解答**：`PuzzleSample.solution_path` 是訓練用的，
  在 `reverse_curriculum_k=None` 下 env 只讀它的**第一個元素**（起點），
  而起點就是編號 1 的位置 ⇒ 從題目本身推得出來。有測試釘住這個不變量。
- **三種回應分清楚**：checkpoint 不存在 → **503**；沒有該尺寸的模型 → **400**；
  跑完沒找到解 → **200 ＋ 說明**（跟既有 solver 一致）。

實測（容器內，`models/` 唯讀掛載）：

```
RL (behaviour cloning)   (200, '(0, 0) -> (0, 1) -> (0, 2) -> (0, 3) -> (1, 3) -> ...')
7x7 via RL               (400, '{"detail":"No RL policy for a 7x7 board; trained sizes are [4, 6]."}')
```

⚠ **分布外**：RL 訓練資料每題是 0 或 2–5 道牆，而 VLM 從真實截圖讀出來的可以 10 道以上
⇒ 從 `/api/vision/solve` 流過來的題目對 RL 是分布外，registry 的說明欄已標注為 experimental。

## 6. Docker：修掉四個「看起來有起來、其實沒有」的缺陷

| 缺陷 | 症狀 |
|---|---|
| 正式 image **沒有 `CMD`** | `docker compose up` 建好 image、容器 Up，**裡面沒有 server**（base image 預設指令是 shell）|
| 開發 image 停在 `tail -f /dev/null` | 靠 `run_docker_dev.py` exec server 進去，但那行**沒有 `-d`**、`subprocess.run` 會一直等 ⇒ 後面的 healthcheck 永遠跑不到 |
| **`models/` 進了 build context** | 每次建置把 **6.6 GB** 送給 daemon |
| 兩個服務都**沒有 healthcheck** | `docker ps` 的 `Up` 不代表服務活著 |

修完後實測（完整輸出見 [`../deployment-guide.md`](../deployment-guide.md) §5）：
兩個容器 `Up (healthy)`、`/api/echo/health` 200、`/ui` 200、`/svelte-ui` 200、
四種 solver 全部 200、不支援的尺寸 400、`/api/vision/solve` 200。

**另外抓到一個設定漂移**：這個 worktree 的 `.env` 停在 2026-08-15 的
`OLLAMA_MODEL_NAME=openbmb/minicpm-o2.6`，卻配著 `finetune` 的 prompt
⇒ 視覺端點回 200 但吐出**全空的 10×10 盤面**。同步成 `.env.example` 的
`zip-qwen35-4b-p4c:f16` 之後，同一張圖讀成 **7×7 並抓到編號**。
**`.env` 不進版控、每個 worktree 一份，所以它會各自過期**——這點寫進部署指南了。

## 8. 這次我判斷錯的地方（記下來比藏起來有用）

1. **外推又錯**：事前用 hazard 0.035 預測 best-of-32 ≈ 0.887，實際 **0.8500**。
   這是本 track 第三次外推失準 ⇒ 規則升級成「hazard 表只能用來**排除**，不能用來**預測**」。
2. **「混合尺寸沒有機制理由改善 6×6」——錯了**（§2）。
3. **「best-of-16 是 16 倍算力」——講鬆了**，實際是 **5.35 倍**（第一次成功就停）。
4. **「新舊資料集的 4×4 是同一批題目」——錯了**：種子相同，但產生器有 0.5 秒的逐次嘗試
   timeout，**負載不同結果就不同**（舊包存活 19,274 題、新包 19,299 題）⇒ 新舊包不可直接比，
   所有對照都在新包上重跑。
