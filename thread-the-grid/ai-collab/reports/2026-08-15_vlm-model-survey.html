1. 結論先講

兩個主力候選，看你要不要付 Colab 的錢：

  • 只想用免費 T4 → Gemma 4 E4B（Apache-2.0、Unsloth 官方 QLoRA 只要 10GB、支援 vision 微調）。關鍵理由：免費 T4 是 Turing 架構、不支援 bf16，而 Unsloth 明說 Qwen3.5 不建議走 4-bit QLoRA → Qwen3.5 在免費 T4 上其實很尷尬。
  • 願意付 CU 用 L4／A100 → Qwen3.5-4B（主力）＋ Qwen3.5-9B（上限對照）。Qwen3-VL-8B 在 DocVQA 拿 96.1、4B 拿 95.3，同代 Qwen 在「讀圖中文字」這條線上是最強的一族，而我們的任務正是讀圖中的數字與線條。

本機部署完全不是瓶頸：9B 的 Q4 量化推論只吃約 6GB，你的 16GB 綽綽有餘（詳見第 2 節）。

再加一組低成本對照：DeepSeek-OCR 2（Unsloth 有官方微調 notebook）。不是因為它一定贏，而是它便宜到值得平行試一輪（詳見第 6 節）。

2. 本機能跑多大？7／8／9B 會吃力嗎

先把兩件常被混在一起的事分開：訓練吃的 VRAM 是推論的好幾倍。

2.1 推論（部署）：9B 一點都不吃力

2B~5 GB~3 GB~2 GB✅ 輕鬆
4B~9–10 GB~5.5 GB~3.5 GB✅ 輕鬆（bf16 也放得下）

這張表是估算（bf16 ≈ 2GB／1B、Q8 ≈ 1.1GB／1B、Q4_K_M ≈ 0.6GB／1B，再加視覺編碼器與 KV cache 約 1–2GB），不是實測。實際值必須在 P0 階段量。影像 token 多時 KV cache 會再吃一點。

直接回答你的問題：7／8／9B 在你的機器上「推論」完全不吃力，Q4 量化後大約 6GB，甚至還能同時開別的東西。真正的天花板在訓練。

3. 為什麼這個任務值得 fine-tune

白話版

現在是「寫一大段說明書＋三個範例，拜託通用模型照格式吐 JSON」。通用模型什麼都會一點，但沒有一項專精，所以時好時壞——尤其數牆壁在第幾條線、圓圈在第幾格這種對位細活。微調等於拿一萬張已知正確答案的圖去補習，讓模型只把這件事做到極熟：說明書從三頁縮成三行，速度變快，答案穩定。

術語版

目前是 few-shot in-context learning ＋ 手工 JSON 解析（output_type=str 混合策略，2025-10-24 驗證，決策見 ai-collab/roadmap.md）。三個結構性弱點：

  • prompt 成本：build_puzzle_prompt() 內嵌三個完整 JSON 範例（final_puzzle_parser.py:131-159），每次推論重付。微調後可縮成一句話。
  • 格式不穩：需要 extract_json_block() 做 regex 兜底（同檔 :46-58）。微調把輸出分布鎖進單一格式。
  • 空間精度：牆是「兩個相鄰格子」的關係（{"cell1":[r,c],"cell2":[r,c]}），通用 VLM 對細粒度相對位置本來就弱，這正是資料能教會的。

任務範圍極窄——輸出只有 layout 與 walls 兩個 key，schema 定死在 SimplePuzzleOutput（final_puzzle_parser.py:37-43）。任務越窄，小模型微調的性價比越高。

4. 開源 VLM 現況調查（2026-08 更新版）

v1 這一節是錯的，先認帳：v1 把 Gemma 3 當現役、把 Qwen3-VL 當主流，兩者都落後至少一代。以下是重新查證後的版本。

4.1 先看大局：2026 年開源前緣發生了兩件事

  1. Qwen 分成兩軌，旗艦轉閉源。Qwen3.7-Max／3.7-Plus（2026-05／06）與 Qwen3.8-Max（2026-08-02）都是 API-only、不放權重；開源線維持在「落後約一代」的中階，最後一個開源通用模型是 2026-04 的 Qwen3.6-27B。官方曾預告 2026-08 第二週釋出 Qwen3.8-Max／3.8-27B 權重，截至本報告撰寫時尚未上架。
    → 對我們的意義：Qwen 最新的「小尺寸開源 VL」仍然是 2026-02 的 Qwen3.5 系列（0.8B／2B／4B／9B），Qwen3.6 沒有 10B 以下。
  2. Gemma 4 出來了，而且首度給 Apache-2.0。2026-03-31／04-02 釋出，五個尺寸 E2B／E4B／12B／26B-A4B／31B 全部支援影像輸入（E2B／E4B／12B 另支援音訊），E2B/E4B 128K context、其餘 256K。這是 Gemma 線第一次拿掉自訂授權改用純 Apache-2.0。

5. 選型推薦：不是「4B 就好」，是分流

Q2：你建議 4B 就好了嗎？

不是。v1 之所以停在 4B，是因為當時把「本機訓練」當硬限制——4B bf16 LoRA 10GB 剛好卡進 16GB，9B 的 22GB 放不下。但你說訓練要放 Colab，這個限制就不成立了：本機只需要跑推論，而 9B 的 Q4 推論只要 6GB。

所以修正後的建議是：用尺寸做對照實驗，而不是先賭一個尺寸。先用 2B／4B 把整條 pipeline 打通（資料、訓練腳本、評估、部署），再用同一份資料訓 9B，看指標差多少——差得少就留 4B（推論快、迭代快），差得多就上 9B（反正本機跑得動）。Unsloth 換尺寸只要改 model name。

6. OCR 專用模型有機會微調成功嗎

Q4：你覺得專門做 OCR 的 VLM 有機會 fine-tune 成功嗎？

有機會，而且值得平行試一輪，但我不會把它當主力。關鍵在於：我們的任務名義上像 OCR，本質上不是 OCR。

6.1 先分清楚我們到底要模型做什麼

把 puzzle_04.png 的解析工作拆開，其實是三件事：

  1. 認字：黑圓圈裡的 1…12。OCR 專用模型的強項——但這是三件事裡最簡單的，通用 4B 模型也幾乎不會錯。
  2. 網格對位：每個圓圈落在第幾列第幾行。空間推理——OCR 模型有版面分析（layout parsing）能力，理論上對「表格化網格」是熟的。
  3. 牆的關係抽取：一條粗黑短棒壓在兩格之間，要輸出「它隔開了 (2,3) 與 (3,3)」。最難——這既不是文字也不是版面框，是一個「圖形元素 → 兩個座標的關係」的抽取任務，OCR 模型的預訓練目標裡幾乎沒有這種東西。

第 3 項才是這個任務的瓶頸，而它正好落在 OCR 專用模型的訓練分布之外。所以「OCR 模型天生比較適合」這個直覺，只在前兩項成立。

6.2 那為什麼還值得試

  • 便宜到不試可惜：PaddleOCR-VL 只有 0.9B，DeepSeek-OCR 3B 級。訓練一輪的時間與 VRAM 都遠低於 4B／9B，等於「用零頭的成本買一個可能的驚喜」。
  • Unsloth 有官方支援：DeepSeek-OCR 有免費 Colab 微調 notebook（Unsloth 稱 OCR-2 訓練快 1.4×、省 40% VRAM、context 長 5×），Paddle OCR 也在其 notebook 目錄。等於這條路的工程成本≈零。
  • 有實證顯示 OCR 模型很吃得下領域微調：有公開回報以 20 萬筆波斯文資料微調 DeepSeek-OCR，僅 60 步就把平均 CER 從 149.07% 降到 60.81%（二手、且是不同任務，只能當「這類模型可被馴化」的旁證，不能當成我們任務的預期值）。

6.3 但要預期到的三個坑

  • 輸出格式被預訓練綁死：這些模型被大量訓練成輸出 markdown／版面 JSON。要它改吐我們的 {"layout":…, "walls":…} 需要足夠資料把舊習慣壓過去。可用「system prompt 指定 JSON」緩解，但微調時仍要注意格式衝突。
  • 指令跟隨能力弱：專用模型犧牲了通用對話能力，prompt 空間小、對複雜指令的服從度不如通用 VLM。我們最終要接 API 與 Gradio，若之後想加「順便判斷網格尺寸」「回報信心度」等，通用模型擴充性較好。
  • 社群微調難度回報：dots.ocr 在 HF 討論串有專門的「微調挑戰與限制」討論。專用模型的微調路徑不像 Qwen／Gemma 那樣被大量踩過。

結論：把 OCR 專用模型排成「B 組實驗」，不是主力。具體做法——資料 pipeline（第 8 節）做好之後，同一份資料多跑一輪 DeepSeek-OCR 2 的 Unsloth notebook，用同一套指標（第 12 節）比較。若它在牆的 F1 上打得贏通用模型，那就換主力；若只是數字認得準、牆一樣糟，就確認了「瓶頸在空間關係而非文字」，這個結論本身也值得寫進報告。

7.2 這對執行計畫的影響

  1. 不要自己寫訓練 loop。fork 對應的 vision notebook，只換三件事：資料集載入、chat template 的樣本格式、評估區塊。

  3. RL 路線先看 Gemma 4 E2B 的 Sudoku GRPO notebook。Sudoku 與 Zip 都是「網格＋硬約束＋可程式驗證」，reward function 的寫法可以幾乎照抄結構（見姊妹報告第 5 節）。

9.1 起手參數

# Qwen3.5 路線（L4/A100）
model = FastVisionModel.from_pretrained("unsloth/Qwen3.5-4B", load_in_4bit=False)   # bf16；官方不建議對 Qwen3.5 用 QLoRA
# Gemma 4 路線（免費 T4）

model = FastVisionModel.get_peft_model(
    model,
    finetune_vision_layers=True,      # 見下方取捨
    finetune_language_layers=True,
    r=16, lora_alpha=16, lora_dropout=0,
)
# 1–3 epoch、lr 1e-4~2e-4、cosine、warmup 5%
# 圖片短邊固定（例如 640），關高解析切塊以省 VRAM
# batch_size=1 + grad_accum 8~16 + gradient_checkpointing
# 多模態 prompt：圖片放在文字之前（Gemma 4 官方明確建議）

關於 finetune_vision_layers 的三層取捨（v2 補充，因為兩家官方建議不同）：

  • Gemma 4 官方建議先設 False，只訓語言／attention／MLP，需要時再開視覺層。
  • 但我們的瓶頸是空間對位（第 6.1 節的第 2、3 項），純語言層很可能學不動牆的位置。
  • 做法：第一輪照官方建議 False 跑（快、穩、當 baseline），第二輪開 True。兩者的 wall F1 差距，就直接告訴你瓶頸是不是真的在視覺端——這是一個很便宜的消融實驗。
  • 另注意：走 vLLM 快速推論（RL 用）時視覺層 LoRA 不支援，要 finetune_vision_layers=False。所以視覺對位能力要在 SFT 這步練好。

11.1 要不要量化？（v2 補充）

不一定要。本機 16GB 扣掉桌面常駐（實測 nvidia-smi 已用 1.9GB）約剩 14GB：

  • 4B → 直接 bf16，不必量化（約 9–10GB），最單純、無精度疑慮。
  • 9B → 必須量化（bf16 約 18–20GB 放不下）：Q8 約 10–11GB、Q4_K_M 約 6GB。

效果會不會掉？三個要點：

  1. Q8 一般視為近乎無損；Q4_K_M 在一般文字生成上損失通常很小——但不能直接把這個通說套到我們的任務。我們要的是精確空間對位＋嚴格結構化輸出，端到端指標又是全有全無（錯一格 → 整題錯），對精度的敏感度高於閒聊。
  2. 好消息：GGUF 的視覺投影檔（mmproj）通常維持 F16，視覺路徑受量化影響比語言路徑小。
  3. 順序不能反：LoRA 要先 merge 成 bf16／fp16 再量化，不要對已量化權重套 adapter。另外 QLoRA 訓練 ≠ 量化推論，是兩件事。

這題不要用推論，要用量測。同一個模型跑 bf16 / Q8 / Q4_K_M 三檔，過第 12 節同一套四層指標，差多少直接看數字。決策規則：若 Q4 的端到端通關率比 Q8 掉超過 2–3 個百分點就用 Q8；4B 就直接 bf16。這個對比在 P0 順手做完。

12. 評估指標

  1. 格式層：JSON 可解析率、通過 SimplePuzzleOutput 驗證率。
  2. 內容層：網格尺寸正確率；waypoint 逐格準確率與完全正確率；牆的 precision／recall／F1（牆最容易漏，必須分開看）。
  3. 端到端層 ★ 最重要：解析結果丟進 CP-SAT，能否解出合法路徑且與 ground truth 一致。唯一真正代表「使用者拿到正確答案」的指標，而且本專案免費就有。
  4. 成本層：本機單張延遲、VRAM 峰值、prompt token 數。

先量 baseline 再訓練。把「未微調模型 ＋ 現有 few-shot prompt」在真實驗證集上的四層指標先量出來。沒有這個數字，訓完無法回答「fine-tune 帶來多少」。

13. 一步到位（agent 看圖直接給答案）

你原本的設計是兩步分開、第一步的產物給人類玩——這個定位保留為主線。但「一步到位」有兩種實作，難度差一個數量級：

B. Agent 一步到位（體感一步，內部兩步）C. 模型端到端（模型自己看圖解題）
內部流程VLM 解析 → 既有 solver 求解 → 視覺化VLM 一次生成完整路徑
正確率上限＝解析正確率（solver 保證最優解）遠低於前者
工作量1–2 天數週起跳，不保證成功
價值產品價值研究價值

13.1 路線 B：建議直接做

POST /api/vision/solve
  input : image (multipart)
  flow  : parse_puzzle_image() -> Puzzle -> prepare_solver_input() -> CP-SAT -> path
  output: {puzzle, path, image_url|gif_url, confidence, parse_warnings}

關鍵設計：回傳解析結果讓使用者能修。既有 Svelte WYSIWYG 編輯器正好吃這個 puzzle——解析錯一兩格時拖兩下就修好。「VLM ＋ 人」的組合拳，比追求 100% 解析率務實。同時保留你原本的定位：解析完的題目可直接進互動分頁讓人自己玩。

13.2 路線 C：三種做法

  1. 工具呼叫式：模型輸出「呼叫 solver 的參數」而非路徑。等於路線 B 換包裝，但可以練 tool-calling（Unsloth 有 FunctionGemma 之類的 notebook）。最務實
  2. 蒸餾式 SFT：用「圖 → CP-SAT 最優路徑」直接教走位。4×4／5×5 可期，7×7 會崩。可當實驗
  3. RL post-training（GRPO/GSPO）：用既有 solver 當 verifier。就是姊妹報告的路線 B，也是目前對「答案可驗證」任務的主流做法；Unsloth 的 Gemma 4 E2B Sudoku GRPO notebook 是最接近的範本。研究題
